# Pinterest: isolated API integration (not deployed)
Official OAuth, owner Firebase ID token (same verification as existing book Worker), encrypted OAuth token at rest, one-time hashed state, D1 submission ledger, no API data cache, no scrape, no password or cookie. Read profile, boards with paging, pin analytics by ID; explicit per-pin publishing with repeat lock, disabled by default. API results are transient, never sent to AI. Reconnect when token expires (refresh token currently not used). Disconnect deletes local credentials and OAuth state; revoke access in Pinterest settings separately. No scheduler yet.

Setup: create an independent Cloudflare Worker (proxy/pinterest-worker.js, compatibility date 2026-11-26), a separate D1 database, apply proxy/pinterest-schema.sql, bind it as PINTEREST_DB. Set OWNER_UID to the owner Firebase UID, PINTEREST_APP_ID, PINTEREST_APP_SECRET and TOKEN_ENCRYPTION_KEY (random 32 bytes as 64 hex chars) as secrets; set PINTEREST_REDIRECT_URI to https://YOUR-WORKER/oauth/callback and register that exact redirect in Pinterest developer app. Never paste secrets into GitHub or chat. Leave PINTEREST_PUBLISH_ENABLED=false until API permission and explicit publishing flow verified. Set the exact deployed HTTPS origin in writer/js/pinterest-api.js via reviewed change, no arbitrary URL entry. OAuth Trial access permits sandbox publishing only; Standard approval is necessary for public Pins. Test owner login, wrong owner denial, state replay, disconnect, expiry, live account data and one chosen sandbox pin before enabling production. No existing Worker, site, Firestore rules or production branch modified. Developer guidelines: https://policy.pinterest.com/en/developer-guidelines ; authentication: https://developers.pinterest.com/docs/getting-started/set-up-authentication-and-authorization/ ; access tiers: https://developers.pinterest.com/docs/key-concepts/access-tiers/.
